# Behaviour difference disclosure (Fabric Mantle vs the original Forge build)

> For what this project is, see [ATTRIBUTION.md](../ATTRIBUTION.md). This file records **every known place where the Fabric build of Mantle behaves differently from the original Forge one**.
> Any change that is not a semantically equivalent replacement gets a row here.

## Why this file exists

Forge patches a lot into vanilla (extra fields, events, registries, access). When Fabric has no counterpart there are only three options:

1. Replace it with the Fabric / Porting Lib equivalent (semantically equivalent → no entry needed)
2. Write our own shim (**approximation** → must be recorded, stating how close it is)
3. Drop the capability entirely (**missing feature** → must be recorded, stating the blast radius)

Every entry below is option 2 or 3.

## The list

| # | Location | Forge behaviour | Fabric behaviour | Category | Blast radius | Verification |
|---|---|---|---|---|---|---|
| 1 | Tag commands (`ModifyTagCommand` / `DumpTagCommand`) | Forge patches vanilla's `TagFile`/`TagEntry`/`TagLoader.EntryWithSource` to support a `remove` list, so a single entry can be removed from **another datapack's** tag | Vanilla's `TagFile` only has `(entries, replace)`. Ours can only append entries, or replace the whole tag (`replace=true`) | Missing feature | `/mantle modify_tag remove` can no longer remove entries owned by someone else, and `dump_tag` no longer shows removals. **This is a Forge-only capability with no equivalent anywhere in the Fabric ecosystem** | Unverified |
| 2 | `CombatHelper` (critical hits) | `ForgeHooks.getCriticalHit` returns an `ICriticalHitEvent`, and a listener can **cancel the crit** with `Result.DENY` | Now uses Porting Lib's `CriticalHitEvent`, which **only exposes `damageModifier`** — there is no result and no cancel | Missing feature | A crit can't be prevented, only its damage multiplier adjusted. TCon tools/modifiers that rely on cancelling crits would stop working | Unverified |
| 3 | `BurningLiquidBlock` / `MobEffectLiquidBlock` | `Entity#getFluidTypeHeight(fluidType) > 0` — an exact measurement of how deep the entity is submerged in that fluid type | Approximation: `entity's foot Y < block Y + fluidState.getOwnHeight()` | **Approximation** | Half-submerged, flowing fluid and non-full-block surfaces may behave differently from Forge. **Worth testing in game** | Unverified (needs in-game testing) |
| 4 | `ItemStackLoadable` (network sync) | Sends only `getShareTag()` (partial NBT, Forge's network optimisation) | Sends `stack.getTag()` (full NBT) | **Approximation** | Packets may get bigger; semantically this is more complete (no data can be lost). Watch bandwidth if some items carry very large NBT | Unverified |
| 5 | `CombatHelper` (item destruction) | Fires `PlayerDestroyItemEvent` | **Closed as N/A**: Fabric has no such event, and no listener on Fabric can subscribe to a Forge event anyway — so this event has no observable effect for either side | Equivalent (no observable difference) | None | No verification needed |
| 6 | `MantleItemLayerModel` (model render types) | Each layer's render type is handed to `CompositeModel` through `RenderTypeGroup` | Porting Lib 2.3.16's `addQuads` doesn't take render types, so each layer's (RenderType, quads) is recorded in `ModelLayers` instead; on the Fabric side Indigo picks the layer per block/item (non-block items are uniformly translucent, blocks are decided by `BlockRenderLayerMap`), so callers that can use it (the book's structure preview, block layer registration) get the right layer | **Shrunk** (Fabric has no per-quad render layers) | Item-type models do end up translucent, which is equivalent to Forge's cutout+translucent for this kind of model; block-type models still need their layer registered on demand | Unverified (needs a visual comparison; `[smoketest] layers/` already reports the measured layer values) |
| 7 | `StructureElement` (book structure preview) | `BlockEntity#getModelData()` supplies the block entity's model data | Uses an empty `ModelData` (Fabric has no `BlockEntity#getModelData`) | Missing feature | The book's structure preview may lose the model data of retextured blocks | Unverified |
| 8 | `DisplayContextLoadable` (network format) | The registry id from `ForgeRegistries.DISPLAY_CONTEXTS` | Reads and writes the vanilla enum in the buffer (`writeEnum`/`readEnum`) | Representation change | **Only affects cross-version / cross-loader compatibility**: consistent within the Fabric side, but incompatible with a Forge side or with an older Mantle. Anything in a save or in NBT that relies on it needs migrating | — |
| 9 | `EdibleItem` (food properties) | Forge's `Item#getFoodProperties(stack, entity)` (stack- and entity-aware) | Vanilla's `Item#getFoodProperties()` (per item) | **Approximation** | Items whose food properties change dynamically with entity state (thirst, status effects) lose that behaviour | Unverified |
| 10 | `ShapedRetexturedRecipe` (recipe ingredient parsing) | Forge's `CraftingHelper.getIngredient(json, flag)` | Vanilla's `Ingredient.fromJson(json, flag)` | Needs auditing | Both take a single boolean, but the semantics (disallow air / allow empty) may be inverted. **Needs checking against the sources** | To audit |
| 11 | `Advancement.Builder#criteria` | Forge loosened it into a directly accessible field | Uses vanilla's `getCriteria()` | Semantically equivalent | None | — |
| 12 | `Holder` | Forge makes `Holder` implement `Supplier` | Vanilla's `Holder` is not a `Supplier`, so `holder::value` is used instead | Semantically equivalent | None | — |
| 13 | `StructureElement` (render layers of the structure preview) | `BakedModel#getRenderTypes(state, random, modelData)` fetches the render type layer by layer and then draws layer by layer (upstream actually draws every layer into the same `TRANSLUCENT_FULLBRIGHT` buffer) | **Closed**: this port reads back the layers our own loader baked from `ModelLayers` and calls `tesselateBlock` once per layer (drawing only that layer's quads each time, into the same buffer as upstream), equivalent to Forge's loop | Equivalent | The book's structure preview is drawn exactly like upstream | Verified (2026-10-01: client started and the book render path showed no problems; the per-layer visuals still need a human comparison) |
| 14 | `NBTKeyModel` (model render types) | `CompositeModel.Baked.Builder#addQuads(renderType, quads)` passes a model-level render type | Same as #6: layers go into `ModelLayers` and the caller uses them | **Shrunk** (same as #6) | Same as #6 | Unverified |
| 15 | `QuadBakingVertexConsumer` (default sprite) | The default sprite is Forge's `UnitTextureAtlasSprite.INSTANCE` (1×1, fully transparent) | Fabric has no such sprite; the default is now a lazily resolved vanilla `missingno` sprite | **Approximation** | The default is only used when a caller **forgets** to call `setSprite`. Every call site in this repository (`MantleItemLayerModel`) sets a sprite first, so this branch is effectively unreachable | Client starts with no errors and the fallback branch is unreachable (no observable behaviour to verify) |
| 16 | `BurnableHangingSignItem` (fuel value) | Overrides `Item#getBurnTime(ItemStack, RecipeType)`, so the fuel value can vary with the stack and the recipe type | Moved to Fabric's `FuelRegistry`: one static value per item, ignoring the recipe type and the stack | **Approximation** | The fuel value in a vanilla furnace is identical; anything that varied by recipe type on Forge (if anything did) is lost | **Verified** (2026-09-29 self-test `fuel/#16 furnace burns it`: `FuelRegistry.get` returns 300; a real furnace was lit and consumed the fuel after 341 ticks, leaving the fuel slot empty) |
| 17 | `MantleShaders` (shader registration) | Forge's `RegisterShadersEvent#registerShader` | Fabric's `CoreShaderRegistrationCallback#register`, with exactly the same registration names and vertex formats | Semantically equivalent | None (only the host and timing of registration differ) | **Measured** (2026-09-29 client start: both the `block_fullbright` and `fluid` shaders were registered through the Fabric callback with no compile or load errors) |
| 18 | `ArgumentTypeDeferredRegister` (argument type sync) | Forge patches vanilla with `ArgumentTypeInfos#registerByClass`, which registers an argument type into the by-class map | Vanilla 1.20.1 has no such method, so an access widener opens the private `BY_CLASS` map and writes into it directly — semantically the exact same step as inside `ArgumentTypeInfos#register` | Semantically equivalent | None | **Verified** (2026-09-29 self-test `argument/#18`: after registering an argument type with Mantle's `ArgumentTypeDeferredRegister`, `ArgumentTypeInfos.isClassRecognized(...) = true` and `byClass(...)` returns the `SingletonArgumentInfo`. **A real client↔server handshake is still untested**) |
| 19 | `ClientSourcesCommand` (client command arguments) | Vanilla's `ResourceLocationArgument#getId(context, name)` (hard-wired to `CommandSourceStack`) | Fabric's client command source is not a `CommandSourceStack`, so the generic `context.getArgument(name, ResourceLocation.class)` is used | Semantically equivalent | None | — |
| 20 | `RenderItem.REGISTRY` / `ColoredBlockModel` / `JsonHelper` / `DefaultRetexturedBlockEntity` | Each one's Forge form (see the mapping table in STATUS.md) | Added the id a Fabric reload listener requires; `bakedBuilder` now explicitly passes `isGui3d=false`; switched to Mantle's own `PacketDistributor`; `getRenderData()` returns `ModelData` | Semantically equivalent | None (`DefaultRetexturedBlockEntity` is in fact a **fix**: it restores the semantics of upstream's `getModelData()`) | — |
| 21 | **Fluid units (global)** | Forge's fluid unit is mB with **1 bucket = 1000**; upstream Forge Mantle's `MantleValues.BOTTLE = 250` | The Fabric Transfer API uses droplets with **1 bucket = 81000**, and `FluidConstants.BOTTLE = 27000`. The 1.11 branch's `MantleValues` already uses `FluidConstants`, so every number datagen produces is 81× larger (for example the `amount` in `fluid_transfer/wet_sponge.json` goes from `250` to `27000`) | **Representation change (incommensurable across loaders)** | Any fluid datapack number **hand-written for Forge Mantle** is off by 81× on the Fabric side; downstream fluid data such as TCon's has to be regenerated with Fabric units. The 23 fluid JSONs under `src/generated/resources` in this repository have already been regenerated in Fabric units | **Measured** (datagen re-run plus a server loading 5 dynamic modifiers normally) |
| 22 | `OffhandCooldownTracker` (CCA entrypoint constructor) | The upstream 1.11 branch lost the 1.20.1 branch's no-argument constructor; CCA instantiates entrypoint classes reflectively, so **the whole mod failed to initialise** (every entity construction threw, and the server crashed as soon as it generated a chunk) | Restored the 1.20.1 branch's `public OffhandCooldownTracker() { this.player = null; }` | **Fix** (a porting regression, not a design difference) | None (restores the existing 1.20.1 behaviour) | **Measured** (before the fix `runServer` crashed; after it the server reaches `Done (28.575s)`, the client starts 92 mods with no errors, and the `cooldown/#22` self-test constructs an `OffhandCooldownTracker` successfully) |
| 23 | `OffhandCooldownTracker`'s NBT read/write | `readFromNbt` writes the tag and `writeToNbt` reads it — **the two were swapped**. CCA's contract is that `readFromNbt` reads the component in from the tag, so cooldown state could never be saved (saving reset the fields to 0) | Swapped the two method bodies back the right way round | **Fix** (an upstream bug present in both branches; not introduced by this port) | Cooldown state now survives saving and loading, which is what it should have done all along | **Verified (unit level)**: the self-test shows `writeToNbt` emitting `{attackReady:40,lastCooldown:40}` (that tag was empty before the fix), and after zeroing it `readFromNbt` restores a `0.0` cooldown; the component also attaches to a real player entity and reads its NBT back. **A real round trip through quit-and-reload has not been tested** |
| 24 | `FluidObject`'s tag API | Upstream 1.11's `FluidObject` offers all three of `getLocalTag()` (this mod's namespace, exact match), `getForgeTag()` (the common namespace, craft-equivalent) and `getTag()` (common if there is one, local otherwise); it also has a `getBlock()` that returns null for non-flowing fluids. `ItemObject` has `getRegistryName()` | The 1.11 branch merged the first three into a single `getCommonTag()` (which returns null when common is null), and `ItemObject` kept only `getId()`. Downstream TCon 3.12.1 calls `getLocalTag()/getTag()/getForgeTag()` in 174 places and `getRegistryName()` in 44, all of which failed to compile after switching Mantle versions | **API restoration** (re-exposing methods upstream already had, without changing the behaviour of the existing ones) | `getTag()` falls back to the local tag when there is no common tag (which is exactly upstream's `getTag()` semantics, and what `FlowingFluidObject` originally did), so downstream code can no longer receive a null tag | **Verified at compile level** (the 218 errors on the TCon side are gone). Not separately verified at runtime |
| 25 | `AbstractIngredient` (base class for custom ingredients) | Upstream Forge's `AbstractIngredient extends Ingredient`: Tinkers' custom ingredients are themselves vanilla ingredients, so they can be passed straight to a recipe builder as an `Ingredient` | The 1.11 branch changed it to `implements CustomIngredient` (Fabric's custom ingredient interface), so all 69 places in TCon that used a custom ingredient as an `Ingredient` failed to compile | **API restoration** (changed to `extends Ingredient implements CustomIngredient`, overriding `toVanilla()` to return itself so Fabric doesn't wrap it a second time) | The `Ingredient` side's `getItems()`/`test()` are still implemented by the subclasses; `getMatchingStacks()` still goes through Mantle's own implementation. Behaviour matches the Forge build (a custom ingredient can go into a vanilla recipe, and can still be registered as a Fabric custom ingredient) | **Verified at compile level** (Mantle's `build` passes and TCon's 69 errors are gone) |
| 26 | `EntityTypeDeferredRegister` (entity registration) | Upstream Forge only has `register(String, Supplier<EntityType.Builder<T>>)`; whether an entity needs its velocity synced is decided by Forge's `EntityType.Builder#setShouldReceiveVelocityUpdates` | Vanilla's `EntityType.Builder` has no such switch (`EntityType#trackDeltas` returns `false` only for a hard-coded table of entity types, and custom entities default to `true`), so a **new** overload taking a `FabricEntityTypeBuilder` instance was added (the parameter is not a `Supplier` so the two overloads can coexist), handing `forceTrackedVelocityUpdates` to Fabric's builder | **API addition** (to preserve behaviour upstream already expressed) | Entities registered with Fabric's builder can still express "force / forbid velocity sync", such as TCon's custom item frame (upstream sets it to `false`; switching to the vanilla builder would have made it `true`). Entities registered with the vanilla builder are completely unaffected | **Verified at compile level**; not separately verified at runtime |

> Rows marked "Unverified" **cannot be considered done until the corresponding gameplay has actually been exercised on a dedicated server or client**.
> The verification ladder is described in [STATUS.md](STATUS.md).

## Three entries to be especially careful about

1. **#3 fluid submersion test** — the only place where we knowingly approximate something that directly decides whether damage/effects trigger, so it has to be tested in game (put an entity at the edge of a fluid surface, and inside a flowing fluid, once each).
2. **#6 render types** — it can compile fine while the visuals quietly degrade; only a screenshot comparison will catch that.
3. **#1 tag remove** — the only **functional capability loss** in the whole port (not a performance or representation difference). Addons that depend on it need to be assessed individually.

## How to update this file

- A new difference → append it to the end of the table and name "behaviour differences" in the commit message
- A difference that has been verified → change "Verification" to "Verified (date + how)", and **do not delete the row**
- A difference that turns out to be a false positive → it may be merged or deleted, but explain why in the commit message
