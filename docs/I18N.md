也就是说：**已有翻译的质量是上游作者的水平，新增翻译是我们（AI）的水平。**
欢迎母语者直接改这些条目 —— 改的时候只改文本，不要动 `%s` / `%1$s` 占位符的数量和顺序，
`./gradlew validateLangFiles` 会检查这一点。

## 校验任务

```bash
./gradlew validateLangFiles      # 独立运行
./gradlew check                  # 已经挂进 check，构建时会自动跑
```

它检查四件事（都是本次真实踩过的坑）：

1. 每个 lang 文件是**合法 JSON**（`en_us.json` 曾经漏了一个逗号，后果是游戏里所有文本变成 key）
2. key 集合与 `en_us.json` 完全一致（不多不少）
3. 每个 key 的**格式占位符数量**与 `en_us.json` 相同（漏掉 `%s` 会让命令输出少一段信息）
4. 没有把 `%1$s`（位置参数）和 `%s`（顺序参数）**混用**在同一字符串里
   —— Java 的 `Formatter` 遇到这种混用不会报错，而是**静默复用第 1 个参数**，
   所以 zh_cn 里 `/mantle tags add` 的成功提示原本会把「数据包路径」显示成「条目名」。

## 还能做什么（未做）

- 更多语言。原版 Tinkers' Construct 的 Fabric 端有 11 个语言文件（`de_de` / `id_id` / `it_it` /
  `ja_jp` / `ko_kr` / `pl_pl` / `sv_se` / `uk_ua` …），Mantle 只有 6 个。
  想扩语言的话，从 TCon 仓库里复用相同 key 的译文是最省事的做法。
- Cloth Config 的枚举取值名（`config.mantle.fabric.fluidUnit` 的 `millibuckets` / `droplets`）
  目前没有独立翻译 key，界面上显示英文枚举名。
- 把 `validateLangFiles` 扩展成「扫描 Java 里引用的翻译 key，检查是否都在 en_us 里」
  （现在只保证各语言之间对齐，不保证 key 真的被用到）。
